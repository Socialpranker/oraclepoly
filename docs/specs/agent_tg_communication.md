# Коммуникация агента с владельцем: Telegram, решения, отчёты

**Статус:** proposal (детализация §9.6 [концепта v2](portfolio_analyst_agent.md))
**Дата:** 2026-07-20
**Владелец:** владелец
**Инфраструктура:** существующий бот — `app/api/telegram.py` (webhook, callback-кнопки), `app/tasks/notifications.py` (`send_admin_message`, `send_admin_message_with_keyboard`), `ADMIN_TELEGRAM_IDS`. Новый слой строится поверх, не рядом.

Единственный читатель — владелец. Каждое сообщение проектируется как ответ на вопрос «что случилось и что от меня нужно», а не как лог системы.

---

## 1. Принципы — каждый выведен из реального инцидента

1. **Вердикт до цифр.** Первая строка отвечает «что случилось и что от меня нужно». Если ничего не нужно — прямо написано «действий не требуется». Читатель решает за 5 секунд, читать ли дальше.
2. **Каждая цифра носит свою семантику с собой.** Инцидент 2026-07-16: алерт «ROI −1058%» оказался суммой per-signal ROI, а не портфельной просадкой — час разбирательства. Правило: в заголовках только деньги в долларах и портфельная семантика; сырые метрики — в evidence-блоке с явной подписью, что это такое.
3. **Одно сообщение — одно решение.** У actionable-сообщения все кнопки относятся ко всему содержимому. Два вопроса — два сообщения.
4. **Расшифровка при первом упоминании.** Внутренние кодовые имена не считаются известными: «D3 (арбитраж связанных рынков)», «G18 (калибровочный эдж)», «virtual (торговля на бумаге, без денег)». Без стрелочных цепочек и жаргона.
5. **Тишина — дефолт, каждый алерт закрывает свой цикл.** Инцидент 2026-07-13: прокси-алерт «истёк N часов назад» слал ежечасно трое суток при живом прокси. Правило: у каждого типа алерта — дедуп-ключ и cooldown; после тревоги обязано прийти ровно одно сообщение «восстановилось» (или «не восстановилось за N часов»), и цикл закрыт. Никаких повторов той же тревоги.
6. **Свежесть и происхождение видимы.** Каждое сообщение несёт метку данных («данные на 08:30, DQ 🟢») и run ID. Утверждение из протухшего клейма (§3.1 концепта) в сообщение попасть не может — карантин.
7. **Кнопка — контракт.** Нажатие делает ровно то, что написано, привязано к снапшоту цифр на момент отправки (executor §4.4: payload hash, TTL, идемпотентность). Результат вписывается редактированием в то же сообщение. Истёкшая кнопка исчезает, остаётся пометка «истекло — данные могли измениться».
8. **Асимметрия ошибок по классам.** Для информационных сообщений ложная тревога дороже пропуска (пороги консервативные). Для денежного риска (🔴) пропуск дороже ложной тревоги (пороги чувствительные, но с закрытием цикла по п. 5).
9. **Каждое решение получает сверку.** Принятое через кнопку решение автоматически пишется в журнал (§9.5 концепта) с ожиданием и сроком; в срок приходит сообщение «ожидали X, получили Y». Решения без обратной связи — источник тихих байесов.
10. **Attention P&L замыкает петлю.** Судьба каждого сообщения логируется (acted / acknowledged / ignored). Тип сообщений, игнорируемый 4 недели подряд, автоматически деградирует в дайджест — с уведомлением об этом (один раз).

### Анти-пример → норма (реальный инцидент 2026-07-16)

Было:
> ⚠️ D42 demote: sum_roi=-1058%, window=30d, n=47

Стало:
> 🟡 **D42 (ML-детектор по событиям) переведён в тень — деньги не задействованы.**
> За 30 дней 47 виртуальных сигналов: типичная ставка теряла 22%, портфельно это −$4.10 виртуальных. Порог демоута сработал корректно. Реальных ставок у D42 не было (стадия virtual).
> Действий не требуется; вернётся в работу только через ручной promote.
> _данные на 09:00 · run #1291 · [🔍 разбор]_

## 2. Анатомия сообщения

```
<эмодзи класса> <Вердикт одной строкой — что случилось / что нужно>

<2–5 строк: что это значит по-человечески, в долларах;
 если решение — что предлагается, что будет если не делать>

[кнопки — только у actionable; TTL написан прямо в сообщении]

_подвал: данные на HH:MM · DQ 🟢|🟠|🔴 · run #N · [🔍 разбор]_
```

- Кнопка `🔍 разбор` есть у каждого сообщения — раскрывает evidence: цифры с подписями семантики, ссылки на run'ы, задействованные клеймы с датами последней проверки. Разбор приходит reply-ответом на исходное сообщение (нить сохраняется).
- Лимит TG 4096 символов: длинные отчёты — краткая версия сообщением + полный `.md`-файл документом к нему.
- Язык — русский; технические идентификаторы (run ID, имена детекторов) — как есть, с расшифровкой.

## 3. Классы сообщений, приоритеты, часы тишины

| Класс | Что означает | Когда может прийти | Кто отправляет |
|---|---|---|---|
| 🔴 СРОЧНО | деньги под риском прямо сейчас; ждём реакции | в любое время суток | event-триггеры риск-реестра, kill-switch, exposure breach |
| 🟠 РЕШЕНИЕ | предложение с кнопками и TTL (уровень L2) | 08:00–22:00 | policy engine через executor |
| 🟡 ВНИМАНИЕ | знать нужно, делать не обязательно (L1) | 08:00–22:00 | аудиты: DQ, клеймы, IPS |
| 🔵 ОТЧЁТ | регулярные сводки по расписанию | по расписанию | циклы §6 концепта |
| ⚪ ДАЙДЖЕСТ | всё остальное, свёрнуто | секция в daily-брифе | агрегатор |

- **Часы тишины 00:00–08:00**: проходит только 🔴. Остальное копится и входит в утренний бриф.
- **Кэп ≤3 actionable (🟠) в день** — предохранитель из концепта; при переполнении лишние 🟠 откладываются на завтра с пометкой в дайджесте (кроме 🔴 — они вне кэпа).
- 🟠 без реакции: одно напоминание reply-ответом на 50% TTL, дальше — истечение fail-closed («не выполнено») и строка в следующем брифе. Повторных пингов нет.
- **Расписание**: daily-бриф 08:30; weekly-бриф понедельник 09:00; monthly — 1-го числа 09:00; quarterly — первый понедельник квартала. Всё — после утренних аудитов, чтобы цифры были свежими.

## 4. Каталог сообщений с шаблонами

Все примеры — на реальных данных проекта, чтобы было видно, как это читается.

### 4.1 🔵 Ежедневный бриф (08:30)

```
🔵 Сводка — 20.07, 08:30. Действий не требуется.

Деньги: банк $1000 · открыто 3 позиции на $16.20 · вчера +$1.10 (2 резолва, оба в плюс).
Живая торговля: D3 (арбитраж связанных рынков) — 5 сделок за неделю, net −$3.40.
  Направление угадывает (8 из 13), теряем на исполнении в тонких стаканах.
  Это известная утечка; фикс (depth-гейт) — №1 в недельном списке.

Изменилось со вчера:
• D42 (ML по событиям) — в тени после демоута 16.07, наблюдаем. Деньги не задействованы.
• Протух клейм «hold-до-резолва лучше TP/SL» (проверялся 05.07, срок 30д) —
  перепроверка назначена на сегодня, до неё держу пометку в решениях, торговлю не трогаю.

⚪ Дайджест: ночной resolve-цикл штатно (41 рынок); 429-фон в норме (520/ч);
  ожидающих решений нет.

_данные на 08:30 · DQ 🟢 · run #1302 · [🔍 разбор]_
```

Правила: секция «Деньги» — всегда первая и всегда в долларах; «Изменилось со вчера» — только дельты, не состояние; пустой день = «Изменений нет» одной строкой, бриф не раздувается. Если DQ не 🟢 — вторая строка брифа объясняет, чему сегодня нельзя верить.

### 4.2 🟠 Запрос решения (L2, с TTL)

```
🟠 Нужно решение до 21:00: снизить ставку D3 вдвое?

Что случилось: за 14 дней D3 (арбитраж связанных рынков) в минусе на $61 при 34 сделках.
Направление верное (нижняя граница 62%), но каждая сделка теряет ~11% на проскальзывании —
входим в тонкие стаканы.

Предлагаю: временно снизить ставку с $5.40 до $2.70, пока не задеплоен depth-гейт.
  Экономия ≈ $15/нед потерь, цена — недобор ≈ $8/нед, если фикс всё исправит.
Если не делать: продолжаем терять ≈ $30/нед при текущем потоке.

[✅ Снизить до $2.70]  [❌ Оставить $5.40]  [🔍 разбор]

_основание: аудит воронки 16.07, 34 сделки · DQ 🟢 · run #1284 · истекает 21:00, потом «не выполнено»_
```

Обязательные элементы: контрфактика «если не делать» (иначе решение не с чем сравнивать); эффект в $/период с обеих сторон; точные значения в кнопках (не «уменьшить», а «до $2.70» — контракт кнопки).

### 4.3 Квитанция (редактирование того же сообщения после нажатия)

```
🟠 → ✅ Принято 19:42: ставка D3 снижена до $2.70.

Исполнение: cap обновлён (receipt #r-311), следующая сделка подтвердит на практике.
В журнал решений записано ожидание «потери сократятся на ~$15/нед».
Сверка с фактом — 27.07, пришлю результат.
```

Отклонение и истечение — той же механикой: `🟠 → ❌ Отклонено 19:42: оставили $5.40 (записано в журнал с твоим комментарием)` / `🟠 → ⏰ Истекло 21:00: ничего не выполнено. Данные могли устареть — если тема актуальна, будет пересчитана заново`.

### 4.4 🔵 Сверка решения (журнал §9.5, приходит в назначенный срок)

```
🔵 Сверка решения от 20.07: снизить ставку D3 до $2.70.

Ожидали: потери −$15/нед. Факт за неделю: потери сократились на $12/нед
(9 сделок, net −$4.20 против −$16.10 неделей ранее). Ожидание сбылось на 80%.

Depth-гейт задеплоен 24.07 — можно рассматривать возврат ставки.
[Вернуть $5.40]  [Оставить $2.70 ещё на неделю]  [🔍 разбор]
```

Каждое решение с кнопки порождает ровно одну сверку. Просроченные сверки (срок наступил, но факт не собран) — отдельная строка в ближайшем daily-брифе, не тонут молча.

### 4.5 🔴 Срочное (риск-триггер, пример — UMA-спор)

```
🔴 Рынок с нашей живой позицией переведён в спор (UMA), 14:02.

«Will X happen by Aug 1» — наша позиция $12.40 на YES, рынок встал в disputed.
Почему это важно: у UMA задокументирован прецедент разворота исхода против факта
(март-2025, атакующий заработал $100–300K при залоге ~$1K). Сам факт спора — сигнал
хвостового риска, независимо от того, что «объективно произошло». Капитал заморожен
до вердикта (обычно 24–48ч, бывает дольше).

[Запросить закрытие позиции]  [Держать до вердикта]  [🔍 история споров категории]

_закрытие пойдёт через существующий V2-путь с его защитами; это запрос, не мгновенный ордер_
_данные на 14:02 · run #1305 · TTL 6ч, потом остаёмся в «держать»_
```

Другие 🔴 того же класса: kill-switch сработал (какой и почему, что заблокировано, как снять), exposure breach, пересечение drawdown-уровня (кнопки — подтвердить снижение кэпов по лестнице §9.3 / отклонить).

### 4.6 🟡 Данные подозрительны (DQ) — и закрытие цикла

```
🟡 Данные подозрительны — риск-решения приостановлены. Торговых действий не требуется.

12% активных рынков без свежего стакана >30 мин (норма <2%). Всё, что зависит от цен
(рекомендации, сверки), встало на паузу до восстановления. Существующие защиты V2
работают независимо от агента.

_следующее сообщение — когда восстановится, или через 6ч если нет · run #1307_
```

```
🟢 Восстановилось за 47 мин (14:49). Причина: залипание WS-подписки после reconnect,
данные дозаполнены. Пауза снята, пропущенных решений нет. Цикл закрыт.
```

### 4.7 🟡 Протухло основание живого решения (claims-реестр)

```
🟡 Протухло основание живого решения.

Ставка D3 опирается на клейм «hold-до-резолва лучше TP/SL» — последняя проверка 05.07,
30-дневный срок истёк. Пока не переверифицирован: в брифах — пометка, торговля не трогается.

[Переверифицировать сейчас (~10 мин работы агента)]  [Продлить на 30д с обоснованием]
```

«Продлить с обоснованием» требует текста-ответа — он уходит в журнал решений (это осознанный оверрайд, квартальное ретро его увидит).

### 4.9 🔵 Месячный отчёт владельцу (1-е число; краткая версия + полный .md файлом)

```
🔵 Отчёт владельцу — июль 2026. Вердикт: ПОКА ДОТИРУЕТСЯ.

Деньги за месяц:  торговля −$20 · сервер −$40 · прокси −$20 · LLM −$10 · комиссии −$10
                  итого −$100 · банк $1000 (−20% от пика $1250)
Чтобы выйти в ноль: нужен торговый net +$80/мес. Текущая траектория: утечки исполнения
D3 (−$60/мес) — главный рычаг; фикс в работе (см. недельный список).

Бенчмарк: безрисковая ставка из IPS дала бы +$40 на этот капитал. Разрыв −$140.

Агент за месяц: изменил 2 твоих решения (ставка D3, карантин майских вердиктов),
нашёл утечек на ~$60/мес, стоил $6 LLM + ~40 мин чтения. Вердикт агента: ОКУПАЕТСЯ.

[Полный отчёт (файл)]  [Отметить прочитанным]  [🔍 разбор]
```

Вердикт операции всегда в первой строке словами (`РАСШИРЯТЬ | УСТОЙЧИВО | ДОТИРУЕТСЯ | НА ПЕРЕСМОТР`); «эджа не хватает на опекс» — легитимный результат, не замалчивается.

### 4.10 🔵 Квартальный (первый пн квартала): IPS + ретро решений + taxonomy sweep

Краткое сообщение + полный файл: сколько решений принято/сверено, точность ожиданий (в % и $), систематические перекосы («3 из 4 оверрайдов thin-book — в минус, паттерн»), доля классов неэффективностей без вердикта, предложения к IPS (только текстом — правка IPS руками, файлом).

### 4.11 🟡 Direction Card (Direction Scout, §4.3.1 концепта) — предложение направления, не находка

Отдельный тип от всего остального каталога: это не вердикт по уже известному вопросу, а предложение **начать** задавать новый вопрос. Confidence явно ниже, чем у любого другого actionable-сообщения, — и это написано текстом, не спрятано в цифрах.

```
🟡 Направление на рассмотрение (не готовая находка, не сигнал к торговле).

Портфель неэффективностей закрывает 4 из 11 классов известной таксономии; за
последний месяц ни одна Hypothesis Card не касалась «resolution-механики» как
класса напрямую (только UMA-риск как platform-риск, не как источник эджа).

Замечено: 3 независимых площадки за последний квартал сменили механизм резолюции
на менее централизованный — это могло изменить структуру spread-capture класса,
который у нас стоит untested с марта.

Первый дешёвый шаг (~1 час агента, без внешних данных): прогнать таксономический
класс «resolution-механика: spread capture» против уже собранной канонической
истории спорных рынков — чисто ретроспективно, ничего нового собирать не нужно.

[Одобрить как standing question]  [Отклонить]  [🔍 почему это не покрыто раньше]

_вход: portfolio_exposure_snapshot + taxonomy sweep 07.2026, НЕ рыночные данные
напрямую · confidence: низкий, это гипотеза о ценности направления · run #N_
```

«Одобрить» превращает Direction Card в новую standing question для обычного research-цикла (§6 концепта) — единственный легальный переход из открытия в проверку; дальше карточка идёт через Hypothesis Card и experiment runner как любая другая. «Отклонить» логируется с формулировкой (если владелец её оставил) и учитывается при следующем прогоне линзы — чтобы то же направление не предлагалось повторно без нового основания. Direction Card рождается только на недельном синтезе (§4.3.1 концепта — двухтиковая частота): 3-дневный монитор молча копит находки и никогда сам не отправляет сообщение, даже при срабатывании. Молчание недельного синтеза (нет накопленных находок) тоже не порождает сообщение — «Direction Scout ничего не нашёл» не новость и не должно занимать место в ленте.

## 5. Cron-слой: кто просыпается, когда и что делает

Модель полностью push — владелец ничего не запрашивает командами, всё приходит само по расписанию, привязанному к тому, как быстро реально меняется то, что проверяется. Каждая строка ниже — это джоба через `scripts/cron_runner.py` (тот же механизм, что уже несёт 60+ существующих задач проекта), не отдельный демон.

**Правило выбора частоты**: тик = период полураспада проблемы. Если утечка исполнения копится часами — проверка раз в день достаточна и дешевле; если риск-триггер (спор по рынку, где открыта позиция) может дорого стоить за минуты — проверка почасовая. Ни одна джоба не чаще, чем нужно её объекту, — иначе тик сам становится источником LLM-счёта и шума.

| Тик | Что делает | Зовёт LLM? | Когда шлёт в TG |
|---|---|---|---|
| **1 мин** | Мониторинг риск-триггеров: disputed-статус на рынках с открытой позицией, kill-switch, exposure breach, drawdown-уровень. Чисто SQL/Redis-проверки, без LLM. | нет | 🔴 немедленно, только при реальном срабатывании |
| **15 мин** | DQ-срез: freshness/completeness/validity/referential integrity текущего снапшота (§4.2 концепта). Детерминированный вердикт GREEN/AMBER/RED. | нет | только при смене статуса (деградация/восстановление) |
| **1 час, после существующего `detector-signals-resolve` в :40** | Воронка исполнения на свежих resolve'ах: где теряются деньги за последний час; stage-aware reject burst; проверка claims-реестра на протухание (что стало старше своего срока годности за этот час). | точечно: если аудит нашёл аномалию — LLM-explainer формулирует «что это значит» под шаблон | 🟡/🟠 если что-то нашлось, иначе тишина |
| **6 часов** | Контрфактический срез: гейт-контрфактика по свежему `gate_shadow_log`, edge decay/regime monitor (rolling Wilson/Sortino), сверка cost ledger. | да, если найдена аномалия крупнее порога — тот же explainer, плюс researcher-линза набрасывает гипотезу причины | как правило копится в daily-бриф, кроме крупных находок (тогда 🟡 сразу) |
| **daily, 08:00** (перед брифом в 08:30) | Полный прогон библиотеки аудитов (§4.2) целиком; сборка daily-брифа; сверка решений, у которых срок сегодня; проверка кэпа/дедупа за сутки. | да: explainer-линза формирует бриф целиком из уже посчитанных детерминированных цифр | 🔵 бриф в 08:30 |
| **weekly, пн 07:00** | Discovery-нога demand-driven (§6 концепта): проверка, появился ли новый data asset/canonical/событие с прошлой недели — если нет, шаг пропускается без LLM-вызова. Если да — researcher + adversarial-линзы. Плюс сборка improvement-очереди по EV/час. | да, только если появился новый повод (событийно, не по расписанию сам факт вызова) | 🔵 недельный бриф пн 09:00 |
| **monthly, 1-го 07:00** | Owner's report: полная агрегация cost ledger + P&L; вердикт операции; вердикт самоокупаемости агента (§9.8). | да, explainer собирает нарратив | 🔵 месячный отчёт 1-го 09:00 |
| **каждые 3 дня, 07:00 — Direction Scout, лёгкий монитор** (§4.3.1 концепта) | Дешёвая проверка «появилось ли новое основание»: детерминированный дифф внутреннего портфеля + узкий `web_search`-прогон по фиксированному списку тем (регуляторные дедлайны, governance используемых механизмов резолюции, новые площадки, публикации по untested-классам таксономии). Почти всегда отрицательный результат. | точечно: узкий classifier-промпт, не полная линза | никогда напрямую — только копит для недельного синтеза; срочная находка (например, подтвердился регуляторный дедлайн) уходит обычным алертом риск-реестра, не как Direction Card |
| **weekly, ср 06:30 — Direction Scout, полный синтез** (шестишаговый пайплайн — §4.3.1.1 концепта) | Один детерминированный SQL-снапшот → построение поисковых запросов из версионированного списка тем → `web_search`/`web_fetch` → детерминированный pre-filter → единственный LLM-вызов синтеза на уже собранном входе → reconciliation. Рождается Direction Card — куда стоит начать смотреть, не что уже нашли. Единственный автономный по выбору направления цикл в системе; поставлен на среду, не понедельник, чтобы не совпадать по дню с improvement-брифом (§6 концепта, пн 09:00) — разная природа находки не смешивается в один день. Время 06:30 — синтез завершается до дневного цикла аудитов (08:00) и не пересекается с пн/1-го 07:00-джобами; находка уходит владельцу в тот же день. | да, ровно один вызов на шаге 5 пайплайна; результат обязательно проверяется против уже отвергнутых классов на шаге 6 | 🟡 отдельным сообщением (см. §4.11), если нашлось; иначе тишина без «ничего не нашли» — молчание само по себе не новость |
| **quarterly, 1-й пн квартала 07:00** | IPS-ревью, ретро систематических байесов по журналу решений, taxonomy sweep портфеля неэффективностей. | да | 🔵 квартальный |

Порядок зависимостей — как в существующем crontab: часовой тик стоит через 5–10 минут после resolve-цепочки (`detector-signals-resolve` :40 → `mv_event_outcome` :45 → `v2-execution-resolve-sync` :50), чтобы аудит смотрел на уже досчитанные данные, не на промежуточное состояние.

**Экономика вызовов LLM** (обновляет §7.1 концепта под push-only модель): 1-минутный и 15-минутный тики — вообще без LLM, это чистые SQL/Redis-проверки; explainer вызывается только когда есть что объяснять (тик нашёл отклонение или настал час брифа), не на каждое пробуждение крона. При месячном объёме находок ≈ несколько десятков в неделю оценка §7.1 (~2M input/0.15M output токенов/мес, ~$4–7 через batch) не меняется — большинство пробуждений крона молчат детерминированно и денег не стоят.

## 6. Как тик превращается в сообщение (или в тишину)

Единый пайплайн для каждого пробуждения крона, от 1-минутного до квартального:

```
1. Джоба досчитывает детерминированные метрики за свой объект (SQL/Redis/агрегация).
2. Сравнивает с порогом/предыдущим состоянием — есть ли отклонение, смена статуса,
   наступил ли срок (сверка, бриф, дедлайн).
3. Если ничего не изменилось и не наступил срок — джоба молча завершается. Это дефолт:
   подавляющее большинство пробуждений (особенно 1-мин и 15-мин тиков) заканчиваются здесь.
4. Если есть что сообщать — только теперь зовётся LLM, и только explainer-линзой
   (или researcher/adversarial — для weekly-находок): на вход идёт уже посчитанный
   снапшот цифр, задача LLM — сформулировать «что это значит» под шаблон §4, не считать.
5. Детерминированный reconciliation сверяет каждую цифру черновика с исходным снапшотом.
   Разошлось — сообщение не уходит, инцидент логируется как ошибка рендера, не как находка.
6. Троттлер (§7.1) проверяет дедуп-ключ/cooldown/кэп — и только после этого шлёт в TG.
```

LLM никогда не решает, стоит ли будить владельца, — это делает шаг 2 детерминированно, по версионированным порогам (та же дисциплина policy-engine-first, что и в §4.3 концепта: LLM объясняет уже принятое решение, не принимает его).

## 7. Механика: анти-шум и кнопки

### 7.1 Дедуп и cooldown (обязательны для каждого типа)

| Тип | Дедуп-ключ | Cooldown | Закрытие цикла |
|---|---|---|---|
| DQ-деградация | источник × вид проверки | 6ч | «восстановилось» / «не восстановилось за 6ч» |
| Риск-триггер | запись реестра × рынок | до смены статуса | вердикт спора / снятие триггера |
| Протухший клейм | claim_id | 7д | переверифицирован / продлён |
| Reject burst (stage-aware) | детектор × стадия | 12ч | поток нормализовался |
| Запрос решения | proposal_id | одно напоминание на 50% TTL | квитанция / истечение |
| Сверка решения | decision_id | однократно | — |

Правило «одно сообщение на инцидент»: продолжение истории — reply-ответом в нить исходного сообщения, не новым сообщением (в ленте один инцидент = одна нить).

### 7.2 Кнопки — привязка к executor (§4.4 концепта)

- `callback_data` = `proposal_id`; approve связывает подпись с payload hash — подтверждаются ровно те цифры, что были в сообщении. Изменился вход (DQ RED, смена снапшота) → proposal инвалидирован, кнопки снимаются редактированием, пометка «данные изменились».
- Повторное нажатие идемпотентно (ключ `session:call_id`): вторая квитанция не создаётся, эффект не дублируется.
- TTL истёк → fail-closed: кнопки убраны, «⏰ истекло, не выполнено». Никакого auto-approve.
- Каждое нажатие пишет `agent_actions` (approval + receipt) и строку attention P&L (acted).
- Кнопки только у L1/L2 действий каталога; L3 (promote to live, ордера, капитал) в этом боте кнопок не имеет — только существующий V2/TG-workflow.

### 7.3 Attention P&L — деградация и возврат

- acted / acknowledged (нажат «разбор» или «прочитано») / ignored — по каждому сообщению.
- Тип с action-rate 0 за 4 недели → деградирует на уровень (actionable → строка в дайджесте → тишина), с однократным уведомлением «этот тип больше не шлю отдельно, разжалую обратно, если увижу спрос».
- Возврат — только ручной (владелец говорит об этом явно, агент фиксирует и повышает уровень); автоматического «повышения» шума нет.

## 8. Реализация поверх существующего бота

- Транспорт готов: `send_admin_message_with_keyboard` + callback-обработчик в `app/api/telegram.py`. Планировщик — существующий `scripts/cron_runner.py` + `crontab.conf`, новые строки по таблице §5, без отдельного демона. Новое: реестр proposal'ов (`agent_actions`), рендерер шаблонов (§4), планировщик сверок из журнала решений, троттлер по таблице §7.1. Существующий throttle/coverage-механизм TG-уведомлений (PR #669/#670) переиспользуется, не дублируется.
- Все шаблоны — код в `app/agent/templates/` (не свободная генерация LLM): LLM заполняет только поля «что это значит» через explainer-линзу (§6, шаг 4), детерминированный reconciliation сверяет каждую цифру шаблона со снапшотом до отправки (§7.2 концепта). Сообщение с несошедшейся цифрой не отправляется — это fail-closed для коммуникации.
- Существующие алерты системы (proxy-health, DB size, зависшие позиции, demote-алерты) мигрируют под эти же принципы постепенно: сначала новые сообщения агента, потом рефактор старых под анатомию §2 (отдельные PR, вне скоупа Phase 0).
- Фазировка: Phase 0 — только 1-мин/15-мин/1-час тики без LLM (чистые SQL-проверки) + 🔵 daily/monthly без кнопок (кроме «разбор»); Phase 2 — 🟡/🟠 + журнал решений + сверки + weekly/quarterly тики; Phase 3 — 🔴 с L2-кнопками через executor; **Direction Scout (§4.11) — только Phase 4, самая последняя строка расписания.** 3-дневный монитор безопасен с первого дня (ничего не отправляет, только копит); недельный синтез — теневой первый месяц (Direction Card генерируются и логируются, не отправляются владельцу) по правилу §8 концепта, несмотря на weekly-каданс самих прогонов.

## 9. Acceptance

1. Ретро-тест на золотых инцидентах: demote D42 (sum-ROI), proxy-спам 07-13, D38→D3 anomaly-kill — рендер по новым шаблонам читается без вопросов «что это значит» (проверка — сам владелец).
2. Каждое отправленное сообщение имеет run ID и проходит reconciliation цифр; несошедшееся — не отправлено и залогировано.
3. Ни один тип алерта не может прийти дважды без закрытия цикла (тест на дедуп-ключи).
4. Нажатие любой кнопки: квитанция редактированием ≤5с, повторное нажатие без эффекта, после TTL — «не выполнено».
5. Каждое принятое решение порождает ровно одну сверку в срок.
6. За неделю обычной работы: ≤3 🟠 в день, ноль повторов, владелец ни разу не спросил «что это значит» (последнее — субъективный, но главный критерий).
